# Прогон, повторная проверка и отчёт

## Панель администратора

На Mac запустите Docker Desktop и откройте `start-genesis.command` из архива. Из Терминала тот же файл запускается командой `bash start-genesis.command`. Панель находится на `127.0.0.1`. После первого открытия адрес с ключом сеанса меняется на обычный адрес панели. Повторно открыть её можно тем же файлом запуска. Для остановки используйте кнопку остановки контейнера `genesis-admin-local` в Docker Desktop. Данные сохраняются в Docker-томе `genesis-admin-data`.

На Linux команда `python3 -m audit_sim serve --state .audit-sim/admin` создаёт панель и печатает локальный адрес входа. Откройте его в браузере на той же машине. Запуск использует одиночного локального администратора. Для контейнера применяется `--host 0.0.0.0` с публикацией порта только на локальный адрес компьютера.

Форма задаёт параметры синтетического эпизода. Название в списке помогает найти запись, а генератор назначает компании отдельное вымышленное имя. Один успешно созданный эпизод добавляет одну траекторию. Genesis записывает её в режиме `train`, поэтому в ней есть итоговая награда. Повторный запуск доступен после сбоя. Если процесс остановили посреди работы, незавершённые задачи вернутся в очередь при следующем запуске.

Кнопка **«Скачать JSONL»** выгружает траектории всех завершённых аудитов. В текущей сборке их собирает скриптовая сверка. Для обучения модели потребуется отдельный алгоритм и проверка эффекта на отложенных эпизодах.

## Ручная сессия

`session` обрабатывает ровно один эпизод. Доверенный запускатель передаёт путь к данным или параметры генератора. Клиент политики работает только со стандартными потоками.

```sh
python3 -m audit_sim session fincheck/fixtures/a08 --output .audit-sim/manual
```

Первая строка вывода содержит `observation` и `info`. Введите одно действие JSON на строку.

```json
{"action":"get_document","doc_id":"DA1K9"}
{"action":"calculator","expression":"2500000 + 2500000"}
{"action":"submit","findings":{"episode_id":"EP-CHK-A08","findings":[]}}
```

Каждый ответ содержит `observation`, `reward`, `terminated`, `truncated` и `info`. В режиме `closed` клиент получает нулевую награду. Итог рассчитывается у оценщика и сохраняется в `reports.json` при использовании `--output`. В режиме `train` клиент получает терминальную награду. Нераспознанный JSON в UTF-8 расходует шаг и записывается как пустое действие. Тайм-аут, закрытие канала или превышение допустимого размера сообщения завершают незаконченный эпизод с `truncated=true`.

Для нового эпизода используйте `python3 -m audit_sim session --seed 900001`. Для дополнительных параметров генератора укажите `--config ПУТЬ` к JSON-файлу с одним объектом. Для каталогов, расположенных отдельно, укажите `session PUBLIC --private PRIVATE`. Используйте эту схему из доверенного запускающего процесса, который управляет доступом агента к файловой системе.

## Проверка записи

```sh
python3 -m audit_sim replay fincheck/fixtures/a08 .audit-sim/manual/trajectories.jsonl \
  --reports .audit-sim/manual/reports.json
```

Повторный прогон проверяет контрольную сумму начального наблюдения, порядок действий, последующие наблюдения, награду, флаги завершения, итоговые метрики и отправленные выводы. Параметр `--reports` нужен для сверки закрытой оценки и восстановления причин завершения, когда тайм-аут или закрытие канала произошли между действиями. Измерения времени пропускаются. Oracle работает на стороне оценщика, поэтому его отчёт идёт без публичной траектории. Для обычных законченных траекторий вместо отчёта можно явно задать `--mode closed` или `--mode train`. Допуски берутся из актуального отчёта или явного `--tolerances`.

В распакованном комплекте проверка обучающих траекторий выглядит так.

```sh
python3 -m audit_sim replay episodes trajectories.jsonl --split train --reports train-reports.json
```

## Диагностика для оценщика

```sh
python3 -m audit_sim score fincheck/fixtures/a08 fincheck/fixtures/a08/control_submission.json \
  --inspection-steps 4 --details
```

Команда использует тот же алгоритм сопоставления и расчёта награды, что и среда. С `--details` видны причины вроде неправильной валюты, неполных доказательств и дубля, а также ID пропущенных ошибок. Этот режим предназначен для доверенного оценщика после прогона.

## Офлайн-отчёт

```sh
python3 -m audit_sim demo --output .audit-sim/demo
python3 -m audit_sim report .audit-sim/manual
```

Откройте созданный `report.html` в браузере. Фильтры по политике и ID обновляют и список прогонов, и средние значения на графике. Можно выбрать награду, F1, точность, полноту или число шагов. У полос награды общий ноль, так что отрицательные значения читаются по той же шкале.

В карточке прогона график «Динамика расследования» показывает, сколько уникальных записей появилось к выбранному шагу. Для отправленных выводов можно переключиться на число ID из ответа, которые уже видны в журнале. Появление ID в журнале показывает ход расследования. Правильность вывода отражена в метриках оценщика. Полосы у заявленных сумм используют отдельный масштаб для каждой валюты.

Скрипт, стили и данные включены в один файл. В архиве `demo-report.html` показывает оба сценария демо, а `train-report.html` — записанные обучающие прогоны.

## Проверка на новых данных

При пакетном запуске `python3 -m audit_sim run episodes --split dev --jobs 2` два независимых эпизода могут обрабатываться одновременно. Действия сохраняются в том же порядке, что и при последовательном запуске. Время политики в этом отчёте измеряется после загрузки и проверки файлов эпизода.

```sh
python3 -m audit_sim benchmark --batches 5 --seed 6217 --output .audit-sim/benchmark.json
```

В каждой группе 20 новых эпизодов, в том числе пять чистых и минимум пять со связанными ошибками. Данные независимо проверяются вместе с 20 преобразованными копиями. На оригиналах запускаются четыре базовые политики и эталонная сверка. На копиях дополнительно сравниваются результаты простой сверки, эталонной сверки и oracle с оригиналами. Опция `--start-index` позволяет повторить выбранную группу с тем же seed. JSON сохраняется после каждой полностью проверенной группы. Это локальная проверка на синтетике, совместимая с офлайн-запуском.

## Проверка ограничений процесса

В контейнере с отключённой сетью ограничения можно задать на уровне процессов и проверить вывод команды.

```sh
python3 scripts/check.py --offline --cpus 2 --process-memory-mib 384
```

`--offline` проверяет, что в сетевом пространстве имён доступен только loopback. `--cpus` задаёт наследуемый список допустимых CPU, а `--process-memory-mib` ограничивает виртуальное адресное пространство каждого процесса. Это отдельная проверка от общего лимита памяти контейнера.

## Сборка архива

```sh
python3 scripts/check.py --archive .audit-sim/genesis-submission.zip
python3 -m audit_sim verify-package .audit-sim/genesis-submission.zip
```

В ZIP есть SHA-256 и размер каждого файла. Проверка также сверяет состав и число эпизодов. Два архива из одного каталога с одинаковыми байтами получаются одинаковыми. Время исполнения в заново рассчитанных отчётах может отличаться между запусками.
